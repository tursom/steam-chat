# 消息级重试机制设计

状态：图片发送第一版已实现。本文记录图片任务的默认策略、接口和恢复边界；文字、贴纸和聊天效果接入同一模型属于后续阶段。回应、媒体播放、历史补拉及 Steam 登录恢复保留各自的处理方式。

## 目标和当前缺口

用户发送一张图片后，暂时故障可以自行恢复；恢复失败时可以在原气泡点击重试，不必重新找图。重试过程中可以看到剩余等待时间、尝试次数，也可以停止等待。已送达但确认丢失时，通过查询原任务恢复状态，避免重复发给联系人。

实现组成：

- `src/server/image-upload.ts` 的 `sendSteamImageAttempt()` 执行一次有阶段记录的 SDK 调用，HTTP 请求使用最多 30 秒的超时，提交之前检查取消、原账号及会话。旧接口保留原来的兼容发送器。
- `src/server/send-operations.ts` 负责统一预算、退避、限流冷却、每账号并发、取消、原图保留和过期清理。网页登录刷新不会重新建立次数预算。
- `chat-service.ts` 提供会话任务接口和受保护原图预览。`/api/config` 的 `sendOperations: true` 表示可使用任务流程，旧客户端仍可调用 `/image`。网页配置请求失败时不会盲目回退到旧发送接口。
- `web/app.ts` 为任务提供原气泡重试、倒计时、停止等待、状态查询和同标签页刷新恢复。WebSocket 实时推送任务版本，HTTP 轮询补偿丢失的更新。
- 现有 WebSocket `requestId` 仅关联请求与回复，不是业务去重键。已安装 SDK 的文字请求和图片提交没有可由本服务指定的上游业务幂等键，不能承诺未知请求在 Steam 上恰好执行一次。

## 用户交互

| 状态 | 气泡示例 | 操作 |
| --- | --- | --- |
| 正在发送 | 发送中… | 保留预览和进度 |
| 自动退避 | Steam 暂时繁忙，8 秒后重试 · 第 2/6 次 | 立即重试、停止重试；限流冷却期内禁用“立即重试” |
| 临时断线 | 等待 Steam 恢复连接… | 停止重试 |
| 已确定失败且可恢复 | 发送失败 · 已尝试 6 次 | 重试发送、移除此提示 |
| 需要修正 | 图片格式不支持／账号授权已失效 | 显示具体原因；修正后重新发送 |
| 结果未知 | 结果未确认，重发可能产生重复消息 | 检查发送结果、仍要发送一份、移除此提示 |
| 已确认成功 | 已发送 | 用真实历史消息替换本地发送状态 |

常规重试继续更新同一气泡，不重复清空输入框，不覆盖后来输入的文字，也不创建第二条乐观消息。保留原始图片 File/Blob 或服务端图片快照，不能把压缩过的预览当成原图重发。

自定义素材在任务激活时读取并保留 Buffer 快照；后来改名、移动或删除素材都不改变这条任务的原图。每次图片尝试仍走新的官方 begin/PUT/commit 流程，不缓存或重放上次上传的 HMAC、提交参数，也不跳过 PUT。

未知结果的“仍要发送一份”是用户明确要求的新发送：分配新任务号、关联原未知任务，旧任务不伪装成已经失败。页面直接解释重复风险，不在后台自动执行这一操作。成功或取消后释放不再需要的原图。

升级前已有的气泡没有服务端任务号，不能补造 ID 后声称原请求已经被去重。只有明确未发送、原账号上下文仍有效且原始负载完整时，才可创建新任务重试；旧的未知记录仍走检查结果和用户明确新发的流程。

## 一份发送预算

服务端发送任务管理器统一决定是否、何时再次调用 Steam。图片适配器改为一次尝试，返回阶段和结构化结果；移除任务路径中的第二层通用发送重试。网页登录刷新只修复会话，后续再次发送仍通过同一调度器，不重置次数或耗时预算。

默认值：

- 一轮包含首次发送，最多 **6 次尝试**，最多 **120 秒**的自动调度窗口。
- 普通临时错误按 **2、4、8、16、30 秒**退避，加入约 ±20% 抖动；等待时间不得超过本轮剩余窗口。
- 明确的限流按有效的 `Retry-After` 执行；没有可靠值时至少冷却 30 秒。同一 Steam 账号共享冷却期，“立即重试”不能绕过它。
- 已开始的任务临时断线时等待现有登录恢复；等待不消耗尝试次数，但计入 120 秒窗口。此方案不默认开放离线时新建发送队列。
- 用户点击“重试发送”开始新一轮预算，累计尝试次数仍保留。重复点击只启动一轮。
- 一个任务最多一个 Steam 调用在执行；图片默认每账号最多 2 个上传任务同时运行，其余排队。等待与计时器不能占住其他任务的执行槽。
- 到达窗口上限只禁止新的尝试。若提交已经开始，超时或停止等待都不能证明 Steam 撤销了该消息，应等待确定结果或转为未知。

每次尝试前重新校验原登录会话、`chat.use`、活动 Steam 账号、联系人和在线状态。账号切换、退出登录、权限撤销会停止未提交的任务，不将原任务悄悄改到新账号。已有图片提交的结果继续按未知或真实回调处理。

取消可以阻止尚未开始的尝试。提交后的按钮只能“停止等待”，不能称为“撤回”或把状态改成未发送。用户停止等待后，若收到可验证的成功回调，仍应更新为成功。

## 什么情况下允许再次发送

将错误拆成两个独立维度，不能只看 HTTP 状态码：

```ts
type Delivery = 'not_sent' | 'may_have_sent' | 'sent';
type SendFailure = {
  delivery: Delivery;
  retryable: boolean;
  phase: 'prepare' | 'begin' | 'upload' | 'commit' | 'text_rpc' | 'unknown';
  code?: string;
  retryAfterMs?: number;
};
```

| 证据 | 自动再次发送 |
| --- | --- |
| 图片 begin/PUT 的临时错误，SDK 确认没有进入 commit | 可以，受预算约束 |
| 请求尚未调用 Steam，因临时离线而暂停 | 可以在恢复后继续，受预算约束 |
| Steam 明确拒绝某次请求，且该错误的协议语义已验证为未接受消息 | 只对明确列出的临时错误重试 |
| 图片格式错误、无效联系人、权限拒绝、账号已切换 | 不自动重试，先处理原因 |
| 图片 commit 超时、文字 RPC 发出后的传输超时 | 不自动再次发送，先查原任务和消息记录 |
| 浏览器到本服务的 HTTP 超时/断线/普通 5xx | 查询原任务；不能据此判断 Steam 是否发送 |
| 消息已发送，JSONL 或 RocksDB 写入失败 | 仅处理存储故障，不能再次调用 Steam |

文字、贴纸和聊天效果不能套用“图片尚未 commit”的证明。通用 `Timeout`、`NoConnection` 或“历史里暂时没找到”均不足以证明未发送。旧接口的 `uncertain` 字段可以作为兼容显示字段；新任务以内部分阶段的发送证据作为判定依据。

## 任务号与请求去重

第一版采用有界的进程内任务。为了让状态丢失时也不会误重发，先由服务器预发任务号，再激活发送；执行接口只能操作已存在任务，不能在找不到任务时自动新建并发送。

1. `POST /api/send-operations`：提交消息类型、活动账号和联系人，创建 `prepared` 任务，返回服务器生成的随机 `operationId`、版本和有效期。此步不调用 Steam。创建请求失败后重试最多产生未激活任务，由短期过期机制清理。
2. `POST /api/send-operations/:id/start`：提交原始文字、图片或素材 ID。服务端读取完整负载、校验限制并生成内容摘要，原子封存负载，再进入发送调度。返回 `202` 和当前状态，不让浏览器一直等待完整退避过程。
3. 同任务再次 `start`：相同负载返回已有状态；不同负载返回 `409`。正在执行或已经成功时都不能再次启动 Steam 调用。创建同内容的新消息应申请新任务号。
4. `GET /api/send-operations/:id`：查询状态、版本、下一次重试时间、当前/累计次数、错误及已确认的历史 `item`。HTTP 或 WebSocket 回复丢失后首先查询这个接口。
5. `POST /api/send-operations/:id/retry`：只接受确定未发送且可重试的状态，带 `expectedVersion`，同一版本只开启一轮。若任务已在发送，返回当前状态，不新建并行尝试。
6. `POST /api/send-operations/:id/cancel`：取消后续调度；提交中则只停止等待并保留不确定性。
7. `POST /api/send-operations/:id/expedite`：带 `expectedVersion` 请求提前尝试；不能绕过账号共享冷却。
8. `GET /api/send-operations/:id/image`：读取任务保留的原图，要求同一创建者、登录会话和活动账号；返回 `private, no-store`，已释放时返回 410。

未知结果明确另发一份时，创建请求包含 `previousOperationId`，新旧任务通过 `previousOperationId/replacementId` 关联。同一未知任务的重复另发请求返回已经创建的新任务号，避免双击或多标签页重复启动另一份发送；原未知记录保留真实状态。

原子封存和激活是同一任务的一次状态转换。并发的两个 `start` 不能都通过，图片请求体不完整时不能调用 Steam。状态更新带单调递增版本，网页忽略旧响应。WebSocket 只负责及时提示，漏收后仍能通过 HTTP 查询恢复。

任务绑定创建者、原登录会话、Steam 账号和联系人。所有读取与修改重新检查权限；任务号不是访问凭据。联系人、类型和封存后的负载不可修改。任务状态的成功 `item.eventId` 用于沿用现有历史/回显去重，不按正文相同合并不同消息。

## 结果未知与进程边界

未知状态先查询任务，合并正常 Steam 回调和归档同步。只有能够关联到原尝试的 Steam 标识才自动转成功；相同正文、图片内容哈希或时间接近不能当作确定关联，查不到也不能自动判失败。

同标签页刷新时，从 `sessionStorage` 恢复任务号、账号、本地气泡标识和刷新前的会话视图，再向服务端查询。这里只保存任务元数据，不保存原图、正文或 Cookie。服务端仍持有原图时可提供受保护的临时预览；如果原图尚未上传，页面提示先停止原任务再重新选择。跨账号登录沿用现有上下文清理，不能显示其他账号的任务。

服务重启、任务过期或清理后，旧 ID 的 `start/retry` 返回 `410` 或明确的状态丢失响应，网页转为“原发送状态已失效，请检查聊天记录”。**不能因为任务不存在就重新执行，也不能自动申请新 ID 补发。** 第一版的去重与恢复保证仅覆盖任务仍存活的当前服务进程，不宣称跨重启的恰好一次发送。

若需要“关闭浏览器、服务器重启后仍保留待发送队列”，应单独增加持久化发件箱：记录不可变负载及每次进入 Steam 提交的边界，恢复时未提交任务可继续，提交中的任务必须先恢复为未知。即便使用 RocksDB，也无法把 Steam 提交与本地状态写入做成一个原子事务，不能因此自动重放未知提交。该能力会增加图片落盘、配额、备份和存储故障策略，首期不默认引入；既有 JSONL/RocksDB 聊天归档的独立写入约束继续有效。

## 资源与并发约束

单图限制 7 MiB，每用户待发送原始负载合计限制为 32 MiB；服务端设置任务负载全局上限 128 MiB、任务总数上限 1000，每用户最多 10 条准备中或活动任务。超过上限时拒绝新任务并保留网页原始负载，不通过淘汰正在发送的任务腾空间。

未激活任务 5 分钟过期；失败且可手动重试的原图保留 15 分钟；成功/取消释放图片，简化的结果元数据保留最多 1 小时并受数量上限约束。底层请求尚未结束时仍计入字节和并发预算，即使网页已经停止等待，也不能借此绕过限额。原图过期后，界面明确要求重新选择图片，不能改用预览。过期清理与执行互斥，缺失任务始终按上面的边界处理。

重试不阻塞用户发送后续消息；因此失败消息恢复成功后，实际到达时间可能晚于后来发送的消息。使用 Steam 的真实时间及 ordinal 排序，不伪造原时间，也不重置已有播放器。此方案不额外引入整段会话的顺序发送队列。

## 实施顺序和验收

前三项已覆盖图片流程；第四项是后续范围。单元及 API 回归见 `test/send-operations.test.ts`、`test/send-operations-api.test.ts`；完整浏览器回归在构建后运行：

```sh
node test/browser/image-send-operations.cjs
```

浏览器测试使用真实本地认证、HTTP、WebSocket、JSONL 和 RocksDB，只模拟 Steam 网络响应及外部播放器，分别验证 1440px 与 390px。

1. 将图片适配器整理为单次调用，补齐结构化发送证据；建立任务状态、统一预算和取消逻辑。网页登录刷新与图片退避共用同一预算。
2. 接入预分配、激活、查询和重试接口，测试并发重复请求、内容冲突、旧任务号、过期、权限撤销以及服务重启。
3. 网页保留不可变负载，原气泡展示倒计时和重试按钮；HTTP 回复丢失、WebSocket 重连和页面唤醒只查询状态，不盲目重发。接入同标签页刷新恢复。
4. 按明确的发送证据扩展文字、贴纸、聊天效果，审查并替代原通用即时重试分支。

必须验证：

- 两次临时故障后恢复，只有一次真正的图片 commit 成功，只归档一个业务事件。
- 网页登录刷新发生在中途时，总尝试次数和截止时间不重置。
- 图片提交成功但回复丢失、文字 RPC 超时、归档暂未出现时，任务不会自动再发一条。
- 双击重试、多标签页重复激活、旧状态响应和相同 ID 不同负载都不会产生并行发送。
- 账号切换、权限撤销、退出登录、取消以及限流共享冷却在退避期间仍有效。
- 服务重启后重复旧任务请求、任务过期后请求，都不会调用 Steam。
- 失败图片可在保留期内从原气泡重试；原图过期、队列已满时有明确提示。
- 桌面和手机的倒计时、状态恢复及重试不会生成重复气泡，不会中断播放器。

验证使用本地后端和安装的 Steam SDK 模拟响应；真实联系人发送实验另行限定范围。
