# 聊天历史 LSM 存储方案

状态：首版已实现。下文为目标设计；首版边界和运行方式见末节及 [运维文档](history-storage-operations.md)。

## 1. 决策与范围

已确认的方向：

- 聊天历史使用支持压缩的 LSM-tree 引擎，不增加 SQLite 聊天查询层，不自行实现冷热分块归档引擎。
- 数据库 key 使用二进制编码。
- 同一条消息独立写入 RocksDB 和 JSONL，两条链路互不依赖提交结果、互不阻塞，数据互为备份。
- RocksDB 负责前端查询，JSONL 保留现有 `steam-chat-import` 输入兼容；两者都直接接收消息，而不是彼此的实时上游。
- JSONL 导入和数据库导出仅用于历史迁移、对账修复或灾难恢复，不是正常实时写入步骤。
- 所有新记录携带所属账号 `steamAccountId`，原有 `id` 继续表示聊天对方。
- 运行时仍只登录一个 Steam 账号，但存储支持多个账号的历史。

推荐引擎为 RocksDB。首版选用 `@harperfast/rocksdb-js@2.8.0`，启动时验证 Zstd 实际生效。现有认证的 `auth.sqlite` 不属于本次改造范围，保持不变。

第一阶段包括双路实时写入、历史导入、会话查询、游标分页、日期定位、对账及双向恢复。不包括全文搜索、多实例写库、多个 Steam 账号同时在线、编辑删除消息和群聊模型扩展。

## 2. 当前实现

相关代码：

- `src/storage/chat-log.ts`：JSONL 追加、规范化、历史读取和会话汇总。
- `src/steam/message-logger.ts`：Steam 消息、回声和远端历史补录。
- `src/server/chat-service.ts`：发送消息、HTTP/WebSocket 查询和实时推送。
- `src/paths.ts`：数据目录和日志路径。
- `../steam-chat-import/import.py`：独立 JSONL 导入服务。

目前历史查询会全量读取日志，再解析、过滤和排序，开销随总历史量增长。改造后使用 RocksDB 有界扫描。

当前默认日志为 `${STEAM_CHAT_DATA_DIR}/logs/chat.jsonl`，未配置时数据目录为项目下的 `data`。代码已有可选 `steamAccountId`，后台 logger 和网页发送文本路径也已传入；仍需验证所有路径及异步账号切换，不能仅凭字段存在就认为覆盖完成。

现有 import SQL 路径读取 `date`、`id`、`name`、`echo`、`message`、`ordinal`，未保存 `steamAccountId`。新增字段保持输入兼容，但不会自动使其 SQL 库具备多账号隔离。Mongo 路径直接插入，不能假设外部消费者都有幂等能力。

## 3. 独立双写架构

```text
Steam 事件 / 网页发送结果 / Steam 历史补录
                       |
             规范化不可变消息 + eventId
                       |
                 非阻塞分发
                /          \
       独立 JSONL 队列      独立 RocksDB 队列
              |                    |
       JSONL writer worker   RocksDB writer worker
              |                    |
           JSONL 文件           RocksDB
              |                    |
        现有 import 服务      后端查询 API → 前端

维护路径（不在实时写入链上）：
JSONL → 显式导入 / 补缺 → RocksDB
RocksDB → 显式导出 / 补缺 → 恢复用 JSONL
```

### 3.1 共享消息，不共享提交条件

消息在分发前完成账号捕获、时间和 ordinal 规范化，并生成随机 128 位 `eventId`。消息对象不可变，两路获得相同的 ID 和逻辑内容，分别编码和持久化。`eventId` 不从 RocksDB 分配，也不依赖 JSONL 文件位置。

新 JSONL 保存 `eventId`、`steamAccountId` 和精确的 `sentAt`，同时保留旧 import 需要的 `date` 等字段。时间和缺失 ordinal 只能在分发前确定一次，不能两路各自生成导致内容不同。`date` 与 `sentAt` 必须表达同一时刻，保持既有日志时区契约。

实时路径禁止以下依赖：

- 先 await JSONL 成功，再提交 RocksDB。
- 先提交 RocksDB，再创建 JSONL 导出待办。
- 由常驻 JSONL tailer 驱动实时入库。
- 一路异常导致另一路入队或写入被取消。
- 用统一的成功布尔值掩盖部分落盘状态。

共享入口只负责构造并分发消息，不执行磁盘 IO。每一路入队分别捕获错误，分别返回状态；不等待慢路完成才交付快路结果。进程关闭时分别在截止时间内排空两路并报告未完成项。

### 3.2 故障与资源隔离

两路使用独立 worker、队列、批次、重试退避、超时、健康状态和有界内存预算。RocksDB native 调用或 compaction 不能阻塞 JSONL writer 的 JavaScript 执行。一个 worker 启动失败时另一个仍应启动；局部 worker 崩溃可独立重启。原生引擎若可能导致宿主进程崩溃，worker thread 不能隔离该故障，实施前决定是否将其升级为独立子进程。

队列达到上限时，只将该路标为落后并告警，健康路继续写入；不无限缓存，不把失败路背压传播给健康路。未送达失败路的消息若已在另一份中落盘，可由后续对账找回。分发尚未送到任意一路就退出的事件则没有本地恢复保证。

配置独立的日志与数据库目录、空间告警和资源配额。默认目录可分别为 `${STEAM_CHAT_DATA_DIR}/logs` 和 `${STEAM_CHAT_DATA_DIR}/chat.rocksdb`；要求磁盘故障隔离时应部署到不同卷。共享磁盘满、进程崩溃、机器断电仍是共同故障，不能仅靠两个队列宣称完全隔离。

### 3.3 状态与失败语义

每路至少具有 `pending`、`durable`、`failed/lagging` 状态，成功分别依据自身持久化确认：

| JSONL | RocksDB | 含义与行为 |
| --- | --- | --- |
| 成功 | 成功 | 双份持久化，历史可查 |
| 成功 | 失败或未完成 | JSONL 副本保留，数据库恢复后可补入；查询可能不完整 |
| 失败或未完成 | 成功 | 历史可查，日志副本待修复；现有 import 可能暂时缺记录 |
| 未成功 | 未成功 | 尚无已确认本地副本，严重告警，不能声称消息已存储 |

Steam 发送状态与两路持久化状态分开。存储重试绝不触发 Steam 重发。单路故障不禁止健康路记录后续消息，也不因 RocksDB 单路故障暂停全部聊天；两路同时不可用时拒绝新的网页主动发送并告警。该发送前检查不能消除检查后故障窗口，也无法阻止远端继续发来消息。

前端实时事件可携带 `eventId` 和分路状态，不必等待慢路；只有 RocksDB 成功时才能承诺数据库可查。数据库不可用时历史接口明确报错，不自动全量扫描 JSONL。内存状态不是持久化证明，进程重启后的完整性通过两份实际数据对账确认。

独立双写不提供跨介质原子性。在至少一路确认持久化后，可以从该副本修复另一路；两路持久化前的共同崩溃可能丢事件。Steam 历史补录仅是尽力恢复，不承诺覆盖所有消息。

## 4. 各路持久化

### 4.1 RocksDB

同一数据库由一个 writer 拥有写权限。启用 WAL，初始使用同步批次提交，完成后才确认该路 durable。每个 `WriteBatch` 原子更新：

- 消息记录和库内记录 ID 分配状态。
- `eventId` 到消息 key 的持久化映射。
- 会话摘要、最近会话索引及被替换的旧索引删除。
- 仅在历史导入时更新源进度及隔离记录。

不保存驱动正常 JSONL 写入的 outbox。writer 串行构建批次，同批同会话、同 eventId 共享暂存状态，避免重复插入或残留旧索引。WriteBatch 不代替并发读改写控制。

确认丢失后使用原 eventId 重试并返回已有记录。已有 ID 但内容不同则报告冲突并隔离，不覆盖。eventId 映射随消息保留，不能按短期请求缓存淘汰，否则旧副本恢复会重复入库。

### 4.2 JSONL

writer 直接从消息分发获得完整记录，不查询 RocksDB。保持每行一条 JSON，按独立批次追加并 fsync 后确认该路 durable；普通 append 成功不等于断电持久化。

记录追加采用至少一次语义。确认丢失或恢复重试可能产生重复行，但必须复用 eventId，不伪造新消息。writer 启动时校验活动文件末尾；不完整尾部先隔离保存，再修复到完整行边界后追加，避免新旧内容拼接成坏行。不修改只读历史导入源。

JSONL writer 独立记录轮转文件清单及封存状态，不依赖 RocksDB 元信息启动或追加。现有 import 继续读取 JSONL；新增字段不改变旧字段含义。外部 SQL 自身的去重不等于所有下游幂等，Mongo 等消费者若要求按 eventId 去重需另行适配。本方案不承诺物理 JSONL 行或外部数据库 exactly-once。

## 5. 二进制 Key 协议 v1

使用默认 bytewise comparator，整数为无符号大端编码，不引入自定义 comparator。数据库元信息记录 schemaVersion、codec 版本和数据库代次；不兼容改动需迁移，不能在同一前缀混用编码。

### 5.1 消息 Key

| 偏移 | 字段 | 字节数 | 编码 |
| --- | --- | --- | --- |
| 0 | 类型前缀 | 1 | `0x10` |
| 1 | 所属账号 SteamID | 8 | uint64 BE |
| 9 | 对方 SteamID | 8 | uint64 BE |
| 17 | 消息时间 | 8 | Unix 毫秒，uint64 BE |
| 25 | ordinal | 4 | uint32 BE |
| 29 | 库内记录 ID | 8 | uint64 BE |

共 37 字节。前 9 字节限定账号，前 17 字节限定会话，后续字段保证稳定时间顺序。最近历史使用反向迭代，无需反转时间编码。

- SteamID 从字符串直接转 BigInt，禁止经过 JavaScript Number；API 仍用字符串。
- ordinal 的 uint32 范围需通过 Steam 接口和旧数据验证。非法值不得截断或取模；不满足时在实施前调整布局。
- 缺失 ordinal 在规范化阶段按确定性规则处理，保留原始缺失状态，不能由两个 writer 分别生成。
- 库内记录 ID 是 RocksDB 自行分配的 uint64，仅用于 key 唯一性和稳定排序，不是跨副本身份。JSONL 不等待它生成。
- eventId 才是跨副本标识，在消息 value 和独立映射中保存；数据库重建可重新分配库内 ID。
- 同时间同 ordinal 的不同事件可以共存，不能只按正文去重。

### 5.2 其他 Key

| 前缀 | 布局 | 用途 |
| --- | --- | --- |
| `0x20` | 前缀 + account(8) + peer(8) | 会话摘要 |
| `0x21` | 前缀 + account(8) + lastTime(8) + peer(8) | 最近会话索引 |
| `0x30` | 前缀 + fileId(16) | 显式历史导入进度 |
| `0x31` | 前缀 + fileId(16) + offset(8) | 非法完整行隔离记录 |
| `0x40` | 前缀 + eventId(16) | eventId 到消息 key 的映射 |
| `0x01` | 前缀 + 元信息类型码(1) | 版本、数据库代次、ID 分配器等 |

fileId 为注册历史源时生成并持久化的 128 位标识，不直接取可变路径。源清单保存文件身份、代次、所属账号和时区。

范围上界使用 prefix 的字节序后继，处理进位和无后继情况；反向迭代检查下界，不跨会话。暂不启用未经验证的固定长度 prefix extractor，不同类型 key 的前缀长度不同。

### 5.3 Value

第一阶段优先使用带版本号的 UTF-8 JSON value，保留 eventId、原始 BBCode、方向、显示名、时间和 JSONL 兼容字段，利用引擎块压缩。二进制 key 不要求同时引入复杂的二进制 value 协议。

来源类型区分实时、Steam 补录、文件导入或修复；文件导入附带 fileId 和 byte offset。恢复时保留原事件数据，不因恢复任务不同而修改内容。图片只存引用或 URL，不存图片二进制。会话摘要保存最后消息 key 和预览信息。

## 6. 账号归属、历史导入与去重

`steamAccountId` 是自己的登录账号，`id` 是聊天对方，`echo` 表示方向。接收、回声、网页发送、图片和 Steam 补录都必须在异步处理前捕获所属会话，不能 await 后读取可能切换的全局活动账号。缺失归属的新事件报告错误，不默默猜测。

旧 JSONL 导入是显式任务，不是正常实时链路。旧记录没有账号或时区时由源清单明确指定；无法判定的记录隔离供管理员处理，不对所有账号开放。时间转换为非负 Unix 毫秒，非法日期不替换为当前时刻。

有 eventId 的文件按 ID 幂等入库并校验内容。旧文件无 eventId 时使用源清单的稳定 fileId 和行起始 byte offset，通过固定版本的带命名空间哈希生成 128 位迁移 eventId；保留原来源，检测 ID 内容冲突。复制文件注册为新源不能保证自动业务去重，迁移前检测重复指纹并提示。

导入完整行，消息及进度原子提交，重启续传。半行不推进，固定源 EOF 半行需处理后再结束任务；非法完整行隔离后原子推进并报告数量。路径变化、截断和替换不能简单 offset 清零，身份不确定则停止该源。

同一 Steam 消息由不同回调重复上报属于业务去重问题，不等于 writer 重试。保留现有回声处理，在统一入口核实发送结果与回声关联，尽可能复用已知事件；不能凭正文相同就合并。新的跨来源去重规则需验证 Steam 标识与 ordinal 语义，不能宣称随机 eventId 自动解决业务重复。

## 7. 对账与互相恢复

两份数据是互补副本，不因为正常查询走 RocksDB 就默认数据库永远更完整。对账在独立维护任务中按账号和事件范围进行，使用完整的 eventId 集合与规范化内容校验；数量相同、最后时间相同都不足以证明一致。哈希比较必须使用版本化的规范编码，不能直接依赖 JSON 字段顺序。

对账使用数据库 snapshot 和 JSONL 已同步完整行边界，并考虑两路正常写入延迟。第一遍出现的单边记录先列为候选，在宽限期后重新检查目标再修复，不能把暂时未落盘当成永久缺失。维护任务分批限速，不占满实时 worker 队列。

- JSONL 有、RocksDB 无：仅补入数据库，复用 eventId，不再广播到 JSONL writer。
- RocksDB 有、JSONL 无：从数据库导出到单独恢复段，再由日志维护流程发布，复用 eventId，不重复写库。
- 两边同 ID、同内容：无需动作，JSONL 重复物理行按同一事件处理。
- 同 ID、不同内容：隔离并报告冲突，不自动选择一边覆盖。

修复任务有持久化任务清单、源快照范围、进度和统计，清单位于独立维护目录，不作为实时写入前置条件。恢复输出先写临时段、同步后原子发布，避免外部 import 读取未完成段。再次修复需识别已发布段和事件，避免无意重复发布；物理重复仍按至少一次边界处理。

数据库完全损坏时从保留的 JSONL 重建新库；JSONL 丢失时从数据库生成恢复文件。重建完成需核对 eventId、内容及隔离报告，再切换目录。只恢复一份确实存在的数据，不能承诺恢复双方都未持久化的事件。

两份均在同一机器或磁盘时，不是抗整机、整盘故障的备份。部署需另外保留异盘或远端备份；应用级独立双写不能替代灾难备份。

## 8. 查询接口

保留现有 HTTP/WebSocket 鉴权入口，底层改用有界 RocksDB 扫描。参数包含账号、对方、limit 和互斥的 before/after 游标或日期定位；默认 100 条，上限 500 条，多读一条判断下一页。

- 返回统一时间正序，反向读取结果返回前翻转。
- 页边界使用完整消息 key，严格排除上一页边界。
- Base64URL 游标包含版本、数据库代次和 key，重建后拒绝旧游标。
- 验证长度、类型、账号、会话及当前权限，游标不是权限凭证。
- 请求内必要时使用 snapshot，不跨分页长期持有快照。
- 历史补录及修复可能插入旧位置，客户端刷新获取；不承诺跨页全局快照。
- 最近会话索引会随消息移动，客户端按账号和好友去重，刷新首屏纠正顺序。
- 旧消息导入不能倒退会话最后活动时间；同批次会话更新不遗留旧索引。
- 数据库暂时漏写但 JSONL 已成功时，展示历史同步落后状态，不把已查到的数据冒充完整历史。

新增分页协议需兼容当前客户端，必要时版本化。前端用 eventId 关联实时事件和已入库消息，不依赖 RocksDB 分配的 ID 才能显示实时消息。

## 9. 压缩、接入与运维

RocksDB 使用 SST 块压缩，不自行压缩每条 value。候选为上层低延迟压缩、底层 Zstd，具体取决于绑定能力和实际测试，不承诺未经测量的压缩率。

明确 block cache、write buffer、compaction 并发、导入限速、WAL 和临时空间预算。日志 writer 与数据库 writer 分别设置内存及 IO 预算；不使用共享网络目录多机写库。

保留未压缩 JSONL 的空间也计入总预算。日志轮转、压缩、删除必须兼顾外部 import 消费进度和备份保留要求，不能仅因数据库存在就删除唯一可恢复副本。压缩后的日志恢复支持可后续扩展，不自行实现新的数据库压缩归档引擎。

当前 Docker 为 `node:26-bookworm-slim`。选绑定前验证：

1. Node 26、bookworm 和目标 CPU 架构可重复构建及运行。
2. Buffer key、双向有界迭代、WriteBatch、同步 WAL、snapshot 可用。
3. 压缩配置实际生效，无静默回退。
4. 句柄可释放，writer 可关闭重启；明确原生崩溃是否要求进程级隔离。
5. 维护状态、许可、原生依赖供应链和升级风险可接受。
6. 支持一致性 checkpoint/backup，或提供停写关闭备份流程。

失败时重新评估 LSM 引擎或封装，不默认回退 SQLite 混合方案。

## 10. 迁移、备份与回滚

1. 建立旧文件清单，指定账号、时区、处理顺序和稳定 fileId，备份源文件。
2. 验证字段、时间、ordinal 和外部 import 输入兼容。
3. 分批导入旧数据，核对消息内容、边界、统计及隔离记录。
4. 切换时排空旧运行时队列并固定旧文件最终边界，补齐尾部后启动独立双写；新 JSONL 使用新代次，避免误当旧源持续消费。
5. 切换数据库查询，确认断开任意一路仍可持久化到另一份，再完成首次对账和双向恢复演练。

Steam 断线切换期间尝试远端历史补录，但明确远端保留窗口的限制。迁移任务不修改外部 import 的 `positions.yml`。

运行中数据库备份使用一致性 checkpoint，不直接复制变化中的目录。JSONL 备份使用已封存文件或受控的完整行边界，保留清单与归属配置。数据库备份包含消息、eventId 映射、索引、元信息和导入进度，不包含驱动正常 JSONL 写入的待办。

回滚优先使用兼容数据库 schema 的应用版本。退回只读 JSONL 的旧版本前先停写并对账，从数据库修复日志缺口后验证完整性，不能假定独立双写必然两边同时齐全。恢复数据库时生成新代次，令旧游标失效。版本升级前备份，不假设任意引擎版本可降级。

## 11. 实施拆分与验收

建议逐阶段交付：

1. 引擎接入与故障隔离验证、真实日志压缩及查询基准。
2. 不可变消息、eventId 和二进制 key codec。
3. 独立双 writer、分路状态、幂等、原子索引和各自恢复。
4. 历史导入、双向对账修复工具及报告。
5. 后端分页、会话查询和前端同步状态。
6. 部署资源隔离、备份、故障注入及上线切换。

验收必须覆盖：

- 停掉 RocksDB、打开失败或提交超时，JSONL 继续接收并同步；反向亦然。
- 单路队列满、慢写和 worker 退出，不取消另一条链路；分别测量健康路延迟。
- 两路都不可用时不报告持久化成功，主动发送保护和严重告警生效。
- 任一路提交前后崩溃、确认丢失与重试，eventId 不变，Steam 不重发。
- 单边落盘后整进程重启，通过对账修复缺口；同 ID 内容冲突不自动覆盖。
- 数据库删除或损坏后从 JSONL 重建；日志丢失后从数据库导出恢复。
- 对账宽限期、实时并发修复、修复任务中断、临时段发布和重复运行。
- uint64 精度、ordinal 边界、前缀进位、同时间多条消息和稳定分页。
- 跨账号游标拒绝、账号切换中事件归属、旧消息不倒退会话时间。
- 半行、非法行、日志轮转、截断、替换、重复源和迁移续传。
- 使用隔离数据库验证现有 import 兼容与重复行行为，不写生产库。
- 实际 Docker 构建、不同卷空间不足、备份恢复和共同故障边界。

基准记录总数据量、JSONL 与 SST/WAL 字节数、峰值空间与内存、各路持久化 p50/p95/p99、队列深度、落后范围、修复吞吐，以及 compaction 和单路故障时的健康路延迟与查询延迟。性能阈值根据目标硬件测试后确定。

## 13. 首版落地说明

- 采用独立子进程隔离两路 writer；各自默认最多 1000 条、16 MiB 队列、15 秒 RPC 超时。查询有独立准入上限，不占掉写入和关闭操作的名额。超时会终止对应 writer 并退避重启，健康路继续工作。
- JSONL 每条追加后 fsync；RocksDB 绑定没有暴露同步 WAL 写选项，因此启用 WAL 并在事务后等待 `flush({allowWriteStall:true})` 再确认。该策略偏保守，不能把普通事务返回当成断电持久化确认；大批导入吞吐仍有批量优化空间。
- 正常 JSONL 保留旧 import 字段，并增加 eventId、steamAccountId、sentAt。两个 writer 不互相读取，也不由数据库 outbox 驱动日志。
- 具有原生服务器时间和 ordinal 的同一消息，在 30 秒有界缓存内关联发送结果、回声及 Steam 补录，复用最早记录的 eventId 和内容。JSONL 仍允许至少一次物理追加，数据库按 eventId 幂等，前端不重复显示。缺少可靠时间或 ordinal 时不按正文合并。
- Steam 历史补录写入两份但不当作刚收到的消息推送；前端保留尚未在数据库查询中确认的实时消息，避免异步落盘时刷新丢失显示。
- 历史 API 首版仅允许查询当前活动账号，明确拒绝其他请求账号；数据库本身按账号隔离并保留多账号记录。离线保存账号的独立选择查询尚未开放。
- 维护工具为显式离线 `import`、`export`、`reconcile`。先在临时 LSM 库中验证完整源和冲突，再修复目标；不启动实时 tailer。非法行和末尾半行会带行号、byte offset 中止并保留源文件，不自动隔离后跳过。
- 首版导入重跑从头扫描，使用稳定源 ID 与 byte offset 派生 eventId 保证已入库事件幂等；尚未实现数据库内源游标续传。对账比较完整数据库和提供的一个完整源，导出新恢复段，不直接改源文件。
- 首版不自动轮转 JSONL、不做在线周期对账，也不维护永久发布段账本。恢复段和源清单由运维管理；运行状态是当前进程 writer 健康状态，不是历史两份数据已完整一致的证明。具体失败及重跑边界以运维文档为准。
- 已覆盖真实引擎 Zstd、二进制分页、重启与异常退出、单路故障、拥塞、互相恢复，以及容器和桌面/手机 UI 验证。未进行真实硬件断电实验，未对生产日志执行迁移。
