# 1Panel chat.jsonl 重复归档与导入停滞排查

排查对象：1Panel 的 `steam-chat`、`steam-chat-import`、`steam-log-sync`。日志数据时间截至 2026-11-03（Asia/Shanghai）；`steam-chat` 部署版本为 `316ce576d14bb1a8935ac5a3d5c3ffd8d316f4ab`。

本次仅检查日志、容器配置和数据库元数据/冲突记录。未改动生产日志、数据库、进度文件或服务配置。统计和报告不包含聊天正文、好友 ID 或凭据。

## 结论与生产证据

### 1. 历史补拉没有持久化幂等，造成重复归档

生产 `chat.jsonl` 为 3,615,381 字节、10,686 条完整 JSON，解析错误为 0。

按 `(steamAccountId, id, echo, message, sentAt/date, ordinal)` 严格比对：

- 2,634 组事件重复，额外重复记录共 4,712 条。
- 按消息时间归属上海时区 2026-11-03：94 个不同事件被写成 243 条记录。其中 54 个事件各出现三次，2 个事件各出现四次。
- 三次重复的样例位于第 10391、10504、10674 行，具有三个不同的 `eventId`，排除了仅仅重复展示同一归档行的解释。
- 第 10449 行起和第 10619 行起有连续 65 条完全相同的事件序列。
- 第 10448–10548 行和第 10583–10683 行分别形成从新到旧的连续 101 条记录段。此处 101 条是观察到的连续段长度，包含实时记录，不表示 Steam 请求上限为 101。

源码链路：

1. `src/steam/message-logger.ts:84` 的 `importAttempts` 仅存于进程内。
2. 同文件第 151–174 行：每次进程首次接收某好友的消息，调用历史补拉。
3. 第 104 行请求最近 100 条，`wantBbcode: true`；第 111 行不排序地遍历返回数组。旧接口同样直接遍历（第 134 行）。这解释了观察到的倒序段。
4. 第 78–81 行：图片有专门的持久化别名路径，其他消息调用普通 `storage.append`；`notify: false` 仅抑制通知，不抑制归档。
5. `src/storage/history-storage.ts:242` 起：普通事件只使用 30 秒、1024 条/4 MiB 上限的内存缓存；缓存外事件重新归一化。即使命中缓存，第 277 行仍向 JSONL 和 RocksDB 入队。
6. `src/storage/history-message.ts:59`：未指定 `eventId` 时生成随机 ID。重启后的同一历史事件因此可作为新事件进入归档和 RocksDB。

只将历史数组改成升序，可以修正补拉段内部的顺序，但不能解决重复写入。追加文件也不能保证整个文件严格按消息时间排序，因为离线历史天然晚于实时消息到达。

### 2. 导入直接卡在 SQL 查重条件与实际唯一键不一致

生产导入器的多次 cron 执行均失败于 `logs/chat.jsonl` 的字节偏移 **78512**，对应第 **238** 行。错误为 `IntegrityError`，冲突键名为 `steam_log.timestamp`。

只读查询 `SHOW INDEX FROM steam_log` 确认当前生产唯一键：

```text
UNIQUE timestamp (uid, timestamp, ordinal)
```

导入器查重条件却是：

```text
uid = ? AND timestamp = ? AND message = ? AND ordinal = ?
```

该记录和数据库已有记录的好友、时间、序号、方向均一致，但正文表现不同：

- 文件记录是普通链接文本，56 个字符。
- 数据库记录是带 `[url]` 标签的文本，129 个字符。
- 两者包含相同的 URL 集合；不是首尾空白差异。

因此查重 SELECT 返回空，随后 INSERT 撞上不包含 `message` 的唯一键。源码位置：`steam-chat-import/db.py:108`、`steam-chat-import/import.py:25`。

`steam-chat-import/import_utils.py:142` 的导入逻辑在整个文件成功处理后才提交 SQL 并保存 checkpoint。异常时回滚并退出。当前 `positions.yml` 长度为 0，因此后续执行会重新扫描，并在同一冲突处失败。**倒序时间本身不会破坏按字节保存的进度；这次进度无法推进的直接原因是 SQL 冲突。**

Mongo 在 SQL 之前逐条写入，且不与 SQL 共用事务。其 upsert 使用 `eventId`（有账号时同时使用账号）。日志中被重新生成的不同 `eventId` 不能凭此规则去重。本次未查询 Mongo 的实际重复数量。

### 3. 进度文件挂载方式还有后续兼容风险

容器配置与 `/proc/self/mountinfo` 均确认：

```text
/opt/steam-chat/positions.yml -> /app/positions.yml
```

这是单文件 bind mount。当前本地源码 `Progress.save` 使用同目录临时文件后 `os.replace`（`import_utils.py:130`）；挂载点文件不能按普通文件方式被原子替换。若部署二进制使用此保存方式，修复 SQL 后仍会在保存阶段遇到挂载点替换错误。

生产二进制 traceback 的行号与当前本地源码不同，不能仅凭本地源码认定该错误已经在生产发生。当前观测到的失败仍全部发生在 SQL 插入阶段。修复时应一并核实二进制版本，并使用目录挂载与独立的状态目录，使原子替换可正常工作；不要将整个应用目录覆盖挂载。

### 4. 同步容器不是本次重复写入的来源

检查到的 `steam-log-sync` 脚本将日志目录通过 rsync 同步到 NAS，并压缩归档名 `chat-*.jsonl`；没有向活动 `chat.jsonl` 追加内容的语句。当前活动文件的重复事件同时具有不同 `eventId`，与应用补拉路径吻合。

## 修复建议与验收

1. 优先修复归档写入的持久化幂等：完整 Steam 事件身份应在重启后仍能查回已有事件，重复补拉不产生新归档行。保留离线补拉能力，不能只关闭历史请求或将进程内集合延长。兼容已有随机 `eventId`，避免切换身份方案时再次整体重复；对缺少可靠时间/序号的数据不要仅按正文合并。
2. 补拉批次按时间、序号升序处理。实时消息与补拉并发仍需由同一事件身份协调，不能靠处理顺序去重。
3. 统一导入器查重与实际 SQL 唯一键的语义。对同一事件的普通文本/BBCode 表现差异进行明确处理并保留可审计记录；真实身份冲突不能用 `INSERT IGNORE` 静默丢弃。若改约束或引入事件身份列，需要先制定并审核迁移方案。
4. 核实部署二进制并将 checkpoint 改为可原子替换的目录挂载；增加“SQL 已提交、保存进度失败后重跑”的回归验证。
5. 写入端与导入端修复后，再单独备份、分析并处理历史重复。不能直接删除全部同正文记录、将进度跳到文件末尾，或对活动 JSONL 做原地排序。

应覆盖的回归场景：同批历史连续补拉、超过 30 秒后补拉、进程重启后补拉、实时与历史交错、合法的相同正文多次发送、普通链接/BBCode 变体、导入异常后重跑、checkpoint 原子替换及容器重建后继续导入。

## 修复与验证记录

导入器修复已提交到独立仓库：`b707a5f`；Mongo 查询索引操作及容器打包补充为 `030d051`。1Panel 已切换至 `steam-chat-import:fix-030d051`，使用只读日志挂载、可写状态目录及 `flock` 单实例循环。

扩大只读预检后确认：除 URL 外，还有表情、图片、OpenGraph、转义字面标签和末尾换行的表示差异。比较规则限定于可验证的 Steam 格式，保留 URL 目标、正文顺序和内部空白；不是笼统删除标签。另有 5 条旧空正文占位记录，只在唯一、同方向的完整 SQL 事件已存在时保留已有内容，并输出不含正文的警告。真实冲突仍停止导入。

生产 Mongo 约有 102 万条文档，原先只有 `_id` 索引，事件 upsert 会反复全表扫描。已增加非唯一的部分索引 `steam_event_lookup_v1(eventId, steamAccountId)`，只索引含 `eventId` 的文档；不删除或合并历史文档。

- 10,688 条生产日志在数据库只读副本中执行实际导入逻辑模拟：无失败，预计新增 SQL 记录 1,183 条。
- 导入器 144 项隔离测试通过；打包镜像的模块加载、格式比较、原子 checkpoint 替换和锁竞争检查通过。
- 生产 checkpoint 已成功保存至 `3,615,987` 字节，与验证时的活动日志大小相同；重新读取原始前缀计算 SHA-256，与 checkpoint 一致。
- 导入器容器再次重建后可读取该 checkpoint，未出现 SQL 或保存进度错误。
- 实际 SQL 总行数从 204,077 增至 205,260，新增 1,183 条，与预检一致。Mongo 的事件查询计划已验证使用 `IXSCAN`。

归档修复采用每条 writer 独立的 SQLite 幂等索引，从各自主副本流式重建已有事件身份，保留旧随机 ID。入队和实时广播前并行解析健康副本，避免先广播临时 ID、落盘后却复用旧 ID。主记录优先于未完成预约，代表选择与扫描顺序无关；完整、可靠元数据缺失时不按正文合并。补拉批次按时间和序号升序处理。

JSONL 扫描只按 ASCII LF 分行，保留正文中合法的 U+2028/U+2029；生产副本确实包含这些字符，不能使用会识别 Unicode 行分隔符的通用行读取器。

- 干净交付树的完整测试 548/548 通过，包含独立 writer 故障、重启、ACK 丢失、索引重建、单边旧副本、未完成预约恢复、legacy 昵称差异和 Unicode 正文。

- 在该副本重放最近 100 条实际历史，JSONL SHA-256 不变；两路均完成 100 次持久处理，缺失的 Rocks 副本复用已有身份。
