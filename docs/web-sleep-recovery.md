# Web 消息休眠恢复

## 原因与范围

网页原先仅接收即时 WebSocket 消息。连接关闭后会重新建立，但连接成功时不补拉历史，也没有处理服务端的 `sync_available` 持久化通知。状态轮询仅在 Steam 状态改变时刷新会话；服务端一直在线时，网页休眠错过的消息就不会自动显示。半断开的连接还可能保持 `OPEN`，阻止创建新连接。

修复复用 [持久化同步接口](android-durable-sync.md)。服务端收到的消息仍分别写入 JSONL 与 RocksDB；网页按 RocksDB 的到达顺序游标补拉，消息发送时间更早的历史补录也能被发现。本次没有改动服务端写入流程。

这是浏览器错过已归档消息的恢复。服务端自身停止、Steam 断线期间未收到的消息属于另一条接收链路，不能仅凭网页同步推断已经归档。若仅 JSONL 保存成功而 RocksDB 失败，仍需按 [存储运维文档](history-storage-operations.md) 显式修复。

## 恢复行为

- WebSocket 建连、当前账号的 `sync_available`、页面重新可见、网络恢复以及浏览器从往返缓存恢复时启动补拉。可见页面的轮询定时器间隔超过 15 秒也按唤醒处理。
- 首次请求 `mode=history&limit=1` 获取同一快照的 `liveCursor`，刷新会话列表和当前消息窗口后建立到达顺序边界。基线请求失败时保留第一次快照，重试不会跳过两次快照之间的新消息。
- 后续每页 100 条，直到 `hasMore=false`；当前消息窗口不受即时缓存 500 条上限截断。成功处理一页才推进游标，中途失败从最后成功页续拉。有效会话内每约 15 秒补拉一次，不依赖 Steam 状态请求成功。
- 补拉及其基线读取、状态及健康检查均有 10 秒期限。唤醒时取消旧请求并重建实时连接；每 5 秒发送应用层 ping，10 秒未收到 pong 则替换连接。状态请求失败不阻塞消息补拉。
- 消息按稳定 `eventId` 去重，允许相同内容的不同消息；补拉按消息时间及 ordinal 排列。恢复更新其他会话的预览，保留日期浏览和向上阅读状态，并复用保留的消息 DOM，避免重置音乐或视频播放器。补拉不触发旧消息的声音、桌面通知或聊天效果。
- 登录身份、账号或访问权限改变会取消并清空旧同步；过期数据库游标收到 409 后重新建立基线。游标仅保留在当前网页会话内，整页重开仍通过正常历史分页读取归档。

## 验证

```sh
npm test
NODE_PATH=/path/to/playwright/node_modules node test/browser/sleep-recovery.cjs
```

浏览器回归使用本地真实 HTTP、会话认证、WebSocket、JSONL 和 RocksDB，不登录 Steam、不向任何联系人发消息。通过 Chromium 生命周期接口冻结页面，断开其连接，再由本地后端归档 622 条当前账号的到达记录及另一账号的隔离记录。恢复过程注入一次分页失败，验证续拉全部页面、相同内容不合并、较早时间的补录、其他会话预览、声音/通知静默、日期窗口、滚动状态和正在播放的 iframe 均保持正确。分别运行 1440px 与 390px 视口。

单元测试另覆盖无 pong 的半断开连接、各类唤醒事件、旧账号响应、取消和超时、初始化基线失败、409 重置，以及状态/健康接口失败时的恢复。
