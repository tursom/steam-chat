# 多图批次顺序：模型与实现

范围是一次点击发送时，输入区中多张图片的排列顺序。先用 TLA+ 找出旧算法的反例，再按用户授权实现有序批次。仅保证同一批次的发送顺序；多个批次、文本及其他会话之间仍可并行，不引入持久化发件箱。源码修改不代表已部署。

## 旧实现及两类乱序

旧版 `web/app.ts` 的 `sendComposer()` 捕获 `getImageDrafts()` 顺序，但 `sendFiles()` 为每张图片同时创建 FileReader；各自 onload 立即调用 `sendImage()`。第二张先读取完，第二张就先请求发送。旧 `/api/send-operations/upload` 按每图请求到达时间登记任务；两阶段 prepare/start 路径也没有批次信息。

即使文件读取、请求到达和任务创建都按 1、2 顺序，`src/server/send-operations.ts` 的 `pump()` 仍允许同账号两个任务同时运行。两个 commit 发出后，Steam 可以先接受第二张。仅改成顺序读文件/顺序上传到本服务不能保证实际接受顺序；逐张等待 Steam 的可靠成功确认则已经采用了候选协议的核心门槛。

检查矩阵分别限制“只顺序读取文件”和“读取、HTTP 到达、负载准备全部有序”。后一种仍能找到提交顺序 1、2、实际接受顺序 2、1 的反例，排除了把网络到达逆序误当作服务端并发乱序的解释。

建模阶段的两个现状刻画测试及输入指纹保存在 [BASELINE.md](BASELINE.md) 指向的缓存证据中。它们分别复现真实前端函数的逆序派发和真实管理器的逆序接受。修复后的 `replay.test.cjs` 提取当前真实前端函数及管理器，验证登记完成前不读取图片、逆序读取仍绑定原位置、逆序激活仍按序发送、unknown 不放行、旧实例登记被拒绝。无批次任务的逆序接受保留为并发对照。替身替换 UI、FileReader 和 Steam 适配器；没有连接真实联系人，也没有凭这些回放宣称已验证真实 Steam 的行为。

## 已实现的协议与模型对应

1. 在激活任何图项前，`POST /api/send-operations/batch` 用一次原子登记让服务端获得不可变的有序批次成员。输入顺序由浏览器提交的名称列表确定，不靠各图请求到达时间或时钟。服务端生成批次和成员 ID；成员绑定账号、会话、联系人及位置，内容由首次启动的哈希绑定。单次最多 10 张，前端限制总大小 32 MiB，服务端仍执行任务和图片内存配额。
2. 各图片的读取、请求传输、校验和负载准备可独立完成；准备好不代表允许向 Steam 提交。模型保守地把整个 Steam 上传适配器串行化，暂不引入并行上传/单独串行 commit 的更复杂方案。
3. 前一张可靠确认成功，后一张才能开始。前一张明确未发送而用户显式取消，等真实在途传输结束并确定不会再 commit 后，才可跳过。失败保持阻塞供用户处理，安全的临时故障在原位置重试；unknown 保持阻塞。
4. 停止等待不等于撤回。提交中的取消必须保持 unknown，旧 commit 可以在超时、取消或服务重启之后才被 Steam 接受。
5. 后项仍依赖前项时保留其状态和对象身份；状态缺失时失败关闭，不能当成成功或自动跳过。批次成员只走已有 ID 的 `/start`，不走创建任务的 `/upload`。登记必须携带 `/api/me` 的进程实例标识 `imageBatchEpoch`，重启后旧登记被拒绝；缺失成员启动返回 410。批次在固定 30 分钟后整批停止，unknown 仍保持未知，不放行后项。刷新恢复只查询任务，不重建、不自动发送。

一次批次之外的会话仍可并行。页面对被前序阻塞的任务显示“等待前一张图片确认”；等待前序时不消耗发送窗口，重试保留原位置。登记失败保留输入区图片，未收到完整有效成员列表时不开始上传；不支持批次的服务端会明确提示刷新或逐张发送。

登记成功回包晚于会话切换时，客户端保存原账号下的任务身份并尝试取消未激活成员；取消失败的迟到身份在恢复接管前不会被普通保存覆盖。上传 `/start` 期间的取消有独立请求状态，不因上传忙碌而丢弃。上述页面竞态不在 TLA 抽象内，由前端及浏览器回归测试补充。

## 模型动作与边界

`ImageBatch.tla` 用同一组环境动作比较旧算法和候选协议：

| 动作/变量 | 含义 |
| --- | --- |
| `ReadFile` / `read` | 独立文件读取完成；旧协议将 onload 和立即发出 HTTP 合为同步一步，`SerialRead` 是“只改顺序读文件”的对照 |
| `SendHttp` / `Arrive` / `LoadImage` | 浏览器请求发出、服务端任务登记、校验/加载完成，允许交错 |
| `ReserveBatch` / `registration` | 候选协议原子登记固定有序成员；旧算法逐图在 Arrive 时登记 |
| `Start` | 对应 Map 扫描及每账号 2 个运行/未结束传输槽；候选同时检查前序可靠结果 |
| `IssueCommit` / `Accept` / `Ack` | 发出提交、Steam 实际接受、服务端观察成功三个独立步骤 |
| `Timeout` / `LoseAck` | 超时可以早于接受；回包丢失可以晚于接受，不将 unknown 当作失败 |
| `TransportError` / `network.pending` | 本地请求已报错结束，与远端 commit 仍可能生效分开；本地传输排空后 unknown 可过期，远端依旧可以迟到接受 |
| `FailBeforeCommit` | 明确未提交的失败，允许原位置一次重试或终止等待处理 |
| `Cancel` / `DrainCancelled` | 取消与底层传输排空分开，提交后取消不能说明未发送 |
| `Expire` / `live` | 终态且传输结束后状态过期；候选保留被后项引用的前项 |
| `Restart` | 服务端进程内状态丢失并拒绝继续启动，但在途 Steam 请求可迟到接受 |

`actual` 由模拟 Steam 的 Accept 独立追加，Start 不写实际接受日志。`network.pending` 用图片与尝试序号标记独立远端提交，避免将本地 promise settle 当作远端已结束。`badGate` 在每次 Start 时由独立的 `Reliable` 前序事实检查是否错误放行，不复用被测 `Gate`。

性质包括实际接受序列严格递增（允许明确取消留下缺号）、不重复接受、不静默释放未确认前序、批次登记不可变和成功意味着接受。登记不可变由固定原子输入构造保证，成功意味着接受由 Ack 的前置条件部分保证；接受序列严格递增本身也蕴含不重复，不能把这些性质数量当成独立证明强度。健康上游及弱公平条件下另查所有成员最终发送；故障场景不要求 unknown 自动变成成功。

## 运行与证据

仓库根目录执行（Python 3.9+、Java、TLC 2.19、项目 Node/TypeScript）：

```sh
TLA2TOOLS_JAR=/absolute/path/to/tla2tools.jar python3 spec/image-batch-order/check.py
node --test spec/image-batch-order/replay.test.cjs
```

检查矩阵在 `cases.json`，结果由脚本生成 [RESULTS.md](RESULTS.md)。输入、配置、日志、退出码、SHA-256 和 manifest 写入用户缓存 `steam-chat-tla/image-batch-*`；关键反例复制到 `traces/`。脚本要求预期失败命中指定性质和退出码，不把解析失败当作发现反例；模型/源码变动后需重跑。

实现补充检查位于 `test/send-operations.test.ts`、`test/send-operations-api.test.ts`、`test/web-image-paste.test.ts` 和 `test/browser/image-batch-order.cjs`。前两者覆盖调度、取消排空、保留/过期、权限及重启边界；前端测试覆盖登记失败、逆序读取和上下文变化；浏览器使用真实本地 HTTP 与上传适配器、模拟 Steam，在桌面和手机宽度检查顺序、unknown、取消及刷新。它们补充实现映射，不能扩大 TLA 模型本身的证明范围。

哨兵检查逆序读文件、完整发送、unknown 与尚未启动的后项共存、头项重试成功、实际经历上传中取消并排空后下一张发送、重启后新增迟到接受确实可达。unknown 共存哨兵只证明场景可达；阻塞的正确性依靠 NoSilentRelease 与对应变异。重启哨兵比较重启时的接受数与当前值，不用重启之前已存在的消息充当迟到证据。

变异分别允许 unknown 放行、重放 unknown、把提交后取消当成未发送、未等上传排空就放行、遗忘前项后自动跳过。遗忘/跳过分别检查策略违例 `NoSilentRelease` 和实际乱序 `AcceptedInInputOrder`：后者必须出现“第一张本地网络结束→unknown→过期→第二张接受→第一张迟到接受”，不能只用未提交取消项的过期冒充乱序。

## 局限

- 单个固定账号、联系人、不可变批次；2/3 张图的故障及健康配置，重启配置使用 2 张图。每项最多 2 次尝试、最多 1 次明确提交前故障、最多 1 次重启。有界检查不是任意规模证明。
- 只验证 Steam **接受顺序**。需要 Steam 成功响应代表已接受；官方客户端展示若另有排序规则、时间戳/ordinal异常或第三方同时发消息，模型不能保证最终屏幕相邻或跨来源顺序。
- 取消前的授权/abort检查必须能阻止尚未发出的 commit；不能在模型里将“停止等待”假设成可撤销已发 commit。底层网络仍可迟到完成。
- 模型的 Repeat reservation 只允许同一逻辑批次、相同成员/顺序的无效果重放。实际 API 不提供登记幂等键，也不会自动重试登记；每次成功登记都会创建新的未激活批次。未收到响应时没有图片启动，旧占位最终整批过期。权限、HTTP 参数校验和内容哈希由独立实现测试覆盖，不能把固定 registration 当成对这些检查的证明。
- 没有模型化实际毫秒超时、重试退避、排队保留期、资源配额、批次数量、多个会话/多个实例或持久化恢复。Start 资格和配额的实现仍需要独立回放测试。
- 依赖保留防止错误跳过，但长期 unknown 会阻塞批次并占用资源。实现设置固定批次保留期，过期时停止所有未完成成员、释放可释放原图，不把过期当成可靠成功。模型不刻画具体 30 分钟及清理器，仅刻画不可因遗忘前项而放行。
- Restart 的 stopped 表示旧批次失效，不是产品整体永久停服；模型假定新进程拒绝旧批次登记和启动。实现通过实例标识与仅 `/start` 路径落实这项义务。兼容的旧单图 `/upload` 仍可创建缺失 ID，批次客户端不调用该路径；模型不证明所有旧接口具有跨重启幂等性，也不证明可恢复活性。没有对真实进程重启时的 Steam 网络包做实验。
- 关闭死锁检查，因为有限场景、未知阻塞和状态丢失可自然停住；不提出“永不阻塞”的结论。健康活性明确排除失败、取消、丢回包和重启。
