# 文字发送：反例、修复与验证

本目录保留旧算法的 TLA+ 反例，并检查当前修正版。生产修改位于 `web/app.ts` 和 `src/server/chat-service.ts`。模型不是对某次实际 HTTP 502 的根因判定，也不能推算故障发生频率。

## 修复后的行为

- **提交后保持不确定性。** 一旦调用 Steam，自动核对、账号/权限检查、SDK 结果处理或归档发生异常，不能构成“没有发送”的证据。服务端在这些异常上保留原状态码及错误语义，设置 `uncertain:true`。提交前失败和经过明确分类的 Steam 拒绝仍返回 `uncertain:false`。
- **文字前端不从 HTTP 状态推断未发送。** 没有 `uncertain` 的 4xx 也保持 unknown，不开放普通重试。服务端标记和前端保守分类分别提供保护。旧图片兼容路径保留自己的分类，避免扩大文字修复范围。
- **历史只提供候选证据。** 同账号、联系人、规范化正文和时间下界匹配时，提示“找到相同内容，但无法确认是否对应本次发送”，不自动删除未知条目、不宣称成功、不把回显分配给某个尝试。新旧发送均可看到相同候选；明确另发不再优先抢占原消息。
- **已有及迟到记录可处理。** 日期/分页/latest、实时及耐久同步都提供候选。手动检查还会扫描本地 `historyItems/historyLive`，所以远端最近 100 条已不包含该记录、或查询失败，也不会丢掉本地已知证据。移除原先的 +30 秒候选上界，保留 -2 秒下界排除明显旧记录。
- **只有本次请求的成功响应自动结束本次发送。** 用户核对候选后可使用现有“移除此提示”；它只移除本地提示，不删除聊天历史、不重发、不声明上游成功。unknown 仍只能检查或明确另发；明确未发送仍可普通重试。

缺少 Steam 上游请求关联标识/业务幂等键时，同正文与时间接近不足以确定原请求的结果。修复后的活性目标是“已有候选最终被解释”，不是“所有未知最终自动判为成功”。因此，真实记录与带有明确说明的本地未知提示可能同时显示；这是保留证据差别的用户可见变化。

## 复现与结果

依赖 Python 3.9+、Java、[TLC 2.19 的 tla2tools.jar](https://github.com/tlaplus/tlaplus/releases)，以及项目的 Node.js / TypeScript 依赖。仓库根目录执行：

```sh
export TLA2TOOLS_JAR=/absolute/path/to/tla2tools.jar
python3 spec/text-send/check.py
# 仅运行实现回放，不需要构建：
node --test spec/text-send/replay.test.cjs
```

模型配置在 `cases.json`。`check.py` 固定单 worker、seed=1、fp=0、512 MiB Java 堆，逐项检查退出码和性质名。默认完整证据写入用户缓存 `steam-chat-tla/`；可用 `--output /outside/repository/new-directory` 指定新目录。保存输入快照、配置、完整输出、退出码、日志及输入 SHA-256、基准提交与工具版本，运行前后检查输入未变。

- [RESULTS.md](RESULTS.md)：最新旧算法/修正版/变异的对照结果及当前源码回放。
- [BASELINE.md](BASELINE.md)：首次发现问题时的历史结果；其指纹对应旧源码，不是当前源码的通过证据。
- `traces/`：旧算法反例、修正版变异反例和当前回放输出。出现旧算法反例是预期结果，不能解读为修复后仍失败。

修改模型或源码后旧结果作废，需要重新运行。脚本不运行全仓测试，也不连接 Steam。后端回放只启动本机临时 HTTP 服务，Steam 网络和归档使用替身。

## 原漏洞与修正对照

| 编号 | 旧算法反例 | 修正与验证 |
| --- | --- | --- |
| F5 | Steam 已接受，SDK 超时；核对时 SDK 身份暂态不一致抛 409，绕过 `uncertain:true` 包装；前端将裸 409 判 failed，身份恢复后普通重试被再次接受 | 服务端保留提交后的 uncertainty；文字前端不信裸状态。真实本地 HTTP→真实前端 api/分类/重试函数回放，接受次数保持 1，普通重试返回 false |
| F1 | 官方客户端的同正文事件被当作本地 A 的确认，A 的未知提示消失 | 只报告候选，不消费或删除 A；独立事件来源检查无错误归因 |
| F2 | A 未知后另发 B，A 的迟到回显因 replacement 优先排序被 B 抢占；B 也未知时被错误移除，A 留下 | 移除独占和优先排序；A、B 均保持各自状态，候选不表示来源 |
| F3 | 日期/分页先将 E 放入 `historyItems`，随后检查返回 E，匹配器因已存在而忽略，并误报“未找到” | 所有历史加载均收集候选；检查扫描本地已知历史并处理重复结果；远端空结果或查询失败仍保留本地证据 |
| F4 | Steam 时间戳超过浏览器开始时间 +30 秒，消息可查询但匹配器拒绝；反复检查不能处理 | 候选没有 +30 秒上限；窗口外记录也明确展示为候选，不把它冒充为请求确认 |

F5 的成立条件是 SDK 身份暂时不同、所选账号与浏览器上下文仍固定；真实切号/撤权通知可能清空页面或阻止操作。回放证明该错误传播链路可执行，不证明生产经常出现该暂态。F5 不是自动重发：漏洞在于错误开放了普通手动重试。

F4 指 **Steam 消息时间戳**超出窗口，而非只是在网络上晚到。回放包含“原时间戳在窗口内，60 秒后才观察到”的对照。旧算法在这种情况下本来可以匹配；修正版两种情况都只提示候选。

## 模型与实现对应

### TextSend.tla：旧算法

保留两个本地尝试、一个外部同正文事件的旧协议，用于重现 F1–F4。`Begin` 包含浏览器发起 HTTP；`Submit/calls` 计数的是服务端 SDK 调用，可能等到浏览器超时后才发生；`SteamAccept`、浏览器 `ObserveUnknown/Success/Rejection` 和历史 `Receive` 分离。`Eligible/Preferred/Winners` 保留原 `-2/+30` 窗口、replacement 优先及已认领/已有历史排除。

`Origin(e)` 是独立观察事实，不允许匹配动作读取；`badAssociation/consumers/stuckCheck` 记录错误关联和未知提示停滞。`ManualCheck` 只抽象空结果/重放已有历史，新记录单独通过 `Receive` 到达。

### TextSendEvidence.tla：修正版

继承旧模型的传输、Steam、浏览器结果及时间动作，但 **不调用旧 Receive/ManualCheck**。`ObserveEvidence` 记录 `evidence`，相当于前端 `textCandidateFound`；它不修改 `echo/claimed/consumers/present/ui`。因此历史不能变成确定的请求确认，也不能独占消息。

`CheckEvidence` 扫描本地历史，模拟 `checkOutgoingText()` 扫描 `historyItems/historyLive` 后处理成功查询；反复返回的已有事件也可成为候选。模型仍允许日期页先加载但尚未收集证据的保守路径，之后检查必须能解释它。

| 性质 | 含义 |
| --- | --- |
| `NoFalseAttribution` | 没有把历史事件确认为错误的本地来源 |
| `UnknownRemainsUnconfirmed` | 没有确定结果时，历史证据不会静默删除 unknown；用户主动移除不属于确认 |
| `EvidenceIsReal` | 每条候选提示必须至少有真实接受事件满足时间下界，不凭空编造记录；正文/账号/联系人固定在模型输入中 |
| `NoStuckKnownCheck` | 自身事件已进入历史后，一次成功检查不应仍完全没有候选解释 |
| `KnownOwnEventuallyExplained` | 在已知自身事件、反复成功检查的公平前提下，最终得到候选解释或原请求完成；它不是确定送达性质 |

`SkipExistingEvidence/KeepThirtySecondWindow` 两个变异分别恢复忽略已有历史和 +30 秒限制，都必须重新违反 `NoStuckKnownCheck`；可达性哨兵证明“真实记录已知、仍 unknown 但已有候选”可达。

### TextSendGuard.tla：提交后错误传播

独立拆分提交、接受、SDK 超时、SDK 身份不同、HTTP 409、浏览器分类、身份恢复和普通手动重试。`PreserveUncertainty` 对应服务端异常标记；`StatusOnlyFailure` 对应旧前端裸 4xx 分类。旧组合产生“failed 但已接受”和接受两份的反例；修正两端、只修服务端、只修前端三种组合分别检查。

`FailureSoundness` 检查 failed 意味没有被接受；`NoUnintendedDuplicate` 检查原发送及其普通重试最多接受一份；`NoAutomaticReplay` 区分手动重试与后台自动重放。明确另发一份不在 Guard 模型范围内，在主模型中作为独立发送，允许两份都接受。

## 实现回放与针对性回归

`replay.test.cjs` 用 TypeScript AST 读取当前前端函数，在 VM 中执行。F1–F4 手工编排 TLC 场景，控制 `Date.now()` 与无参 `new Date()`，候选的真实来源保存在 VM 外，不传给生产函数。API/DOM/权限是替身；日期页边界可直接构造。不是自动解析 TLC 轨迹后全栈回放，也不以有限测试证明无限活性。

F5 临时加载当前真实服务端 TS 及依赖，在 `127.0.0.1` 临时端口接收真实前端 `api()` 的请求。只模拟 Steam 接受/超时/SDK 身份，验证真实 HTTP 响应含 `uncertain:true`，以及身份恢复后普通重试不新增接受次数。其他回放覆盖裸 HTTP 错误、明确拒绝后的重试和双击防护。

针对性集成测试另见：

- `test/text-send-check.test.ts`、`test/text-send-reconciliation.test.ts`：真实 HTTP 下核对期间 401/403/409/503、查询成功/失败、SDK 与结果处理异常、明确拒绝及发送次数。
- `test/web-history.test.ts`：前端历史、候选、原请求确认、上下文、重试及草稿回归。
- `test/browser/outgoing-messages.cjs`、`test/browser/text-manual-actions.cjs`：1440px/390px 下候选与未知提示、HTTP 成功、人工移除、原始草稿/内容、限流和重复点击。

## 假设与局限

- 单账号、联系人、规范化相同正文；两个本地尝试和一个外部事件，时间取 `0/1/31`。不是任意规模证明；时间抽象未枚举所有毫秒/漂移。
- 主模型的明确接受/拒绝互斥是协议前提；本轮未逐个验证 Steam 错误码契约。基础安全项由计数门槛和动作定义部分保证，变异只验证检查灵敏度，不证明抽象覆盖了所有实现路径。
- 没有覆盖图片协议、多实例、服务重启、浏览器刷新、完整 SDK 历史双请求、归档一致性、任意多轮普通重试、真实切号及撤权通知。Guard 仅允许一次普通重试和一个暂态 SDK 身份分歧。
- 历史在模型中单调，旧 `claimed` 不遗忘；实际页面历史可替换，旧版集合最多 1000 项。旧“一事件一启发式认领”不包括直接 HTTP 确认，也不是事件终身去重性质。
- 活性只描述存在/排除某类抽象循环，假定保持当前会话并持续成功检查。真实检查有 24 小时入口、最近 100 条、超时及权限约束。未知可能合法地长期存在；刷新或用户移除不等于确认。
- 有限时间/场景可以自然终止，所以关闭死锁检查，不提出无死锁结论。模型变异没有修改生产实现，不能称为实现变异测试。
- 缺少原请求身份时，F1/F2 不可能靠更换排序或扩大时间窗口解决；因此修正了确认语义，并相应将 F3/F4 的活性目标改成真实展示候选。持久化文字发件箱/任务结果查询仍属独立后续工作，本次未引入。
