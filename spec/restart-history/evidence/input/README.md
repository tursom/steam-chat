# 重启后的 Steam 历史恢复：有界 TLA+ 模型

此目录保留重启恢复协议的规格、可复跑检查器和 TLC 证据。生产实现位于 `src/steam/history-recovery.ts`、`src/steam/message-logger.ts` 和 `src/steam/friend-message-events.ts`，对应实现回归位于 `test/restart-history-recovery.test.ts`。模型通过不代表生产已经部署或已恢复实际消息。检查结果见 [RESULTS.md](RESULTS.md)，反例摘要见 [COUNTEREXAMPLES.md](COUNTEREXAMPLES.md)，完整反例在各项 `evidence/<case>/tlc.txt`。

观察到的旧 `src/steam/message-logger.ts`：`onFriendMessage` 才调用 `maybeImportSteamHistory`，请求前向 `importAttempts` 加入账号/联系人键；`getFriendMessageHistory` 使用 `maxCount: 100`，失败后尝试旧接口，但不清除已尝试状态；没有 loggedOn 恢复。这里只刻画有效历史接口仍失败、回退也无法提供完整历史的允许场景，不假定回退一定成功。

## 状态机与实现协议

`RestartHistory.tla` 将以下动作拆开，可在它们之间故障、崩溃或切换账号/连接轮次。

| 动作 | 协议含义 |
| --- | --- |
| `Discover(source)` | loggedOn/friendsList 触发主动发现，将 active Steam sessions、本地会话、好友三种来源合并；3 联系人配置每个来源各独占一个联系人 |
| `Start(contact)` | 逐联系人开始一轮扫描，捕获账号和连接轮次；完成缓存仅当前轮次有效 |
| `IssueQuery` | 验证捕获的令牌后发出查询，包括后续分页查询 |
| `ReadPage` | 独立的异步响应交付，再次验证令牌，读取上游按 time+ordinal 排序的一页 |
| `Commit(event)` | 逐事件耐久归档；允许一页只归档部分时故障/崩溃，重试从头扫描 |
| `Advance` | 页内全部提交后，以最旧事件的 time+ordinal 严格向前分页 |
| `Finish` | 上游已穷尽且最后一页所有事件提交完成，才记当前轮次完成 |
| `Fail` / `Timeout` | 查询错误、归档错误、查询超时；保留已耐久提交的记录，不写完成缓存 |
| `RetryTimer` | 定时重试抽象，将失败任务重新开放给调度器 |
| `Crash` / `LoggedOn` | 清空 volatile 发现/完成/尝试/任务状态，保留耐久归档，再登录并重新发现 |
| `Switch(account)` | 同账号新连接或切换到另一账号；递增轮次、重置完成/发现，保留旧异步闭包以检查迟到回调 |
| `DropStale` | 丢弃失效轮次的任务，释放串行扫描器 |

每个账号/联系人有固定的 3 个上游事件。事件 1、2 的正文、方向和秒相同，ordinal 分别为 1、2；事件 3 在更早一秒。默认页容量 1，另检查容量 2；小页代表旧算法 100 条页限的结构，不声称检查了真实 100 条或 SDK 参数。排序按 time 降序、ordinal 降序，游标严格小于上一页末尾的二元组。最后一页恰好满页时通过剩余候选数确定穷尽，抽象了可靠的 has-more 标志；真实接口若无此标志，必须继续请求直至空页，不能因“拿到满页”完成。

实现每页发送 `startTime: 1`，因为 Steam 协议声明省略/零下界会启用近期 cutoff；模型假定历史响应完整，此参数是实现兑现该假定的必要条件。实现允许页边界重叠并复用现有耐久去重，不会将最早时间减一秒。`Commit` 对应订阅并等待 `onDurable` 的 RocksDB 确认；`append` 的入队返回不足以完成恢复。实际队列按联系人串行执行，每次登录清空 volatile 完成状态，失败默认 30 秒重试，请求/耐久确认默认 15 秒超时。

新增实现回归使用真实 `createHistoryStorage`，覆盖 205 条同秒消息、不同 ordinal 的重复文字/贴纸、部分恢复后重启、边界重叠、live/history 并发以及 sync 游标可见性；其余故障回归使用可控 SDK/存储替身覆盖发现失败、旧接口抢救、超时、无关/缺失耐久确认、账号/轮次切换和 SDK 替换后的事件重绑。这些是手工编排的实现测试，不是自动从 TLC 轨迹生成的全栈回放，也不连接 Steam。

模型的归档是独立耐久记录集合 `archive`，包含实际写入分区 `bucket` 与事件来源 `owner`。事件身份使用账号、联系人、方向、秒、ordinal；正文不参与同一事件的识别。`receipts` 仅是已处理事件的观察集合，用来发现错误去重将不同 ordinal 的事件吞掉。提交时不会直接将整份上游历史放入归档。`Finish` 不读取归档全量集合作为前置条件，只依赖实际分页及提交进度，因此提前完成、截断和游标错误能违反独立的完整性检查。

## 检查性质与反例

| 性质 | 观察事实 |
| --- | --- |
| `CompleteOnlyArchived` | 被标记完成的联系人，其上游历史必须已全部在当前账号分区归档 |
| `AccountIsolation` | 每条实际写入的分区与事件原账号一致 |
| `NoFalseMerge` | 每条已处理事件都有对应的原始事件归档，同文同秒不同 ordinal 不能互相替代 |
| `UniqueDurableIdentity` | 每个耐久身份最多一条记录（集合/原子唯一键的存储抽象，不能据此证明真实存储实现） |
| `NoStaleCallbacks` / `NoStaleQueries` | 任意响应、提交、推进、完成或发出查询时，捕获的账号/轮次必须仍有效 |
| `Recovery` | 在公平调度与有限故障/崩溃/切换下，最终持续在线，当前账号所有联系人历史齐全且本轮完成 |

反例是预期失败：旧算法无入站消息时静默缺失；有入站时单页截断；候选协议变异覆盖单页结束、失败缓存阻止重试、开始即完成、去掉轮次隔离、去掉账号与轮次令牌导致账号串写、只在回调检查但允许旧任务继续查询、按正文和秒去重、只按秒推进游标。失败缓存用活性性质检查，避免只检查“完成才完整”而让永不完成的实现通过。

`no_round_guard` 保留账号检查而移除轮次检查；同账号重连后即可观察到迟到回调。`no_token_guard` 移除整个令牌检查，单独检查实际账号串写；这是整个保护删除的变异，不能声称仅删账号检查而保留全局轮次检查也必然串写。`stale_followup` 只移除查询发出前的检查，回调仍拒绝失效任务，性质仍能抓到不该发生的后续查询。

三个可达性哨兵以刻意违反 `Never...` 不变量的方式，验证部分归档后崩溃、重扫发生精确身份重放后成功；失败后定时重试并恢复；三种来源独占的联系人全部恢复。哨兵的预期失败说明场景可达，不是安全性质被破坏。

## 复跑

Python 3.9+ 与 Java 可用时，在仓库任意位置运行：

```sh
python3 /root/dev/steam/steam-chat/spec/restart-history/check.py \
  --jar /absolute/path/to/tla2tools.jar --implementation
# 也可通过 TLA2TOOLS_JAR 指定 jar；--timeout 默认每项 120 秒。
```

脚本实际执行 TLC 全状态枚举，不使用模拟输出；单 worker、固定 seed=1、fp=0、堆 512 MiB。每项保留可直接运行的 `.tla`、`.cfg`、完整原始日志和命令，`evidence/input` 保留规约输入快照，manifest 记录 SHA-256、Java/TLC 版本、状态数及退出码。实现源码/测试另存哈希以绑定检查时版本。TLC 临时状态文件在本目录内创建并删除；报告和证据也仅写本目录。再次运行会覆盖同名报告/证据，不会修改生产或测试。`--implementation` 另需已安装项目 Node.js 依赖，执行构建和新增重启回归，将完整日志保存在 evidence；不加该选项只检查模型。

成功项必须 TLC 退出 0 并明确报告未发现错误。安全反例必须退出 12 且命中精确的不变量名。TLC 2.19 活性报错正文只输出通用的 `Temporal properties were violated.`，故检查器要求配置中**唯一 PROPERTY 的精确名字**等于预期名，并核对退出 13、实际反例轨迹以及停滞/循环结尾；不能把任意报错当作 Recovery 反例。超时、解析错误、其他性质先失败都使整次检查失败。

## 公平性、假设和边界

- `FairSpec` 对每个来源发现、每个联系人开始、请求、回调、每个事件提交、推进、完成、重试定时器、丢弃旧任务和登录施加弱公平；不对可选故障、切换、崩溃施加公平。`Recovery` 本身不作为假设。稳定环境下持续可用的步骤最终执行，因此活性依赖上游响应与耐久写入最终可用、重试定时器实际运行、发现最终成功，而不只依赖收到新消息。
- 上游固定且在整个恢复期间保留数据、分页响应完整可靠、time+ordinal 能唯一定位且稳定严格推进。没有建模滚动保留窗口、边扫边新增/删除、错误的 SDK 空响应/has-more、Steam 不支持的分页参数、同 ordinal 重用或缺少身份字段。活性不能覆盖已被上游删除的离线消息；缺少完整身份时不可用正文猜测合并。
- 状态空间有界：1 或 3 联系人、2 个账号、每联系人 3 事件、页容量 1 或 2；预算最多各 1 次故障、崩溃、账号/轮次切换，所有预算可选发生。有限预算是“故障最终停止且连接最终稳定”的有界替代，不是对无限次间歇故障或任意数量重启的证明。组合配置同时允许上述三种扰动，但不强迫它们发生；哨兵补充关键路径非空性。
- 一个串行工作器可处理多个联系人，旧异步任务可能在连接切换后交付。崩溃会清空任务；没有模拟旧进程跨崩溃继续执行（正常进程崩溃后不会继续回调）。同一进程的重连/账号切换保留旧闭包，以实际探索旧回调交错。
- 单条 `Commit` 抽象为原子耐久 upsert，真实存储需要兑现唯一身份、持久性和账号分区语义。模型不含 append 已落盘但回执丢失的独立步骤；崩溃后从头重扫及身份重放覆盖其重复归档结果。没有证明真实 JSONL/RocksDB、fsync、跨进程并发或部分写损坏的行为。
- 发现抽象为每个来源最终成功返回固定完整集合；没有发现 API 的单独请求/响应、超时或旧发现回调。实现仍须将相同令牌验证用于这些回调。模型故障点覆盖历史请求/超时/逐条持久化，不能拿此结果替代发现 API 的实现检查。
- 关闭 deadlock 检查，允许有限任务终态及旧算法静默停住；活性检查仍考虑 stuttering，旧算法因此确实产生不恢复反例。未使用状态裁剪、对称约简或将不安全状态排除在外的约束。

这些结果用于审查恢复协议及实现义务，不是实际 Steam 集成、生产部署确认或任意规模的数学证明。运行行为和限制另见 [恢复说明](../../docs/restart-history-recovery.md)。
